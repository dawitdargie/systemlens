Six domain models.

* Repository
* Technical Facts
* Project Understanding
* Project Profile
* Explanation
* Chat Message

Nothing more.

## 1. Repository

Represents the analyzed GitHub repository.

### Source

GitHub API (`GET /repos/{owner}/{repo}`)

### Attributes

| Attribute | Type | Description |
|-----------|------|-------------|
| `name` | string | Repository name (e.g., `"gin"`) |
| `owner` | string | Repository owner/login (e.g., `"gin-gonic"`) |
| `url` | string | HTML URL (e.g., `"https://github.com/gin-gonic/gin"`) |
| `defaultBranch` | string | Default branch name (e.g., `"master"` or `"main"`) |

---

## 2. Technical Facts

Represents deterministic facts extracted by the Light Analyzer (manifest parser + Docker parser). No AI involved.

### Source

`lib/analyzer/manifest-parser.ts` and `lib/analyzer/docker-parser.ts`

### Attributes

| Attribute | Type | Description |
|-----------|------|-------------|
| `language` | string | Programming language (e.g., `"Go"`, `"TypeScript"`, `"Python"`, `"JavaScript"`) |
| `framework` | string | Detected framework (e.g., `"Gin"`, `"Next.js"`, `"Express"`, `"Django"`, `"Unknown"`) |
| `deployment` | string | `"Docker"` if Dockerfile/docker-compose present, otherwise `"None"` |

### Detection Logic

- **Manifest files**: `go.mod`, `package.json`, `requirements.txt`, `Cargo.toml`, `composer.json`, `Gemfile`, `build.gradle`, `pom.xml`
  - `go.mod` → `parseGoMod()` — detects Go + framework (Gin, Echo, Fiber, Chi, Gorilla Mux)
  - `package.json` → `parsePackageJson()` — detects TS/JS + framework (Next.js, React, Express, Vue, Angular, Svelte, Fastify)
  - `requirements.txt` → `parseRequirementsTxt()` — detects Python + framework (Django, Flask, FastAPI, Tornado)
- **Docker files**: `Dockerfile`, `docker-compose.yml`, `docker-compose.yaml`
  - `parseDockerfile()` — requires a `FROM` instruction
  - `parseDockerCompose()` — requires a `services:` key

## 3. Project Understanding

Represents the AI's interpretation of the repository. Generated by Groq (OpenAI-compatible SDK) via `lib/ai/generate-understanding.ts`.

### Source

Groq API (`POST /chat/completions`) with structured JSON response format

### Attributes

| Attribute | Type | Description |
|-----------|------|-------------|
| `purpose` | string | 2-3 sentences explaining what the project does |
| `mainModules` | `ModuleInfo[]` | Array of 3-5 key modules, each with name + description |
| `architectureSummary` | string | 3-5 sentences describing architecture pattern, layers, design decisions |
| `keyFeatures` | string[] | Array of 3-6 main capabilities or features |
| `techStackDetails` | string | 1-2 sentences explaining how detected tech stack is used |
| `dataFlow` | string | 2-4 sentences describing data entry, movement, and exit |

### ModuleInfo Sub-structure

| Attribute | Type | Description |
|-----------|------|-------------|
| `name` | string | Module/component name |
| `description` | string | 1-sentence description of the module |

### Examples

#### Purpose
> "Online food delivery platform for connecting customers with local restaurants."

#### Main Modules
> - Authentication: Handles user login and session management
> - Orders: Manages order creation, status, and history
> - Payments: Processes payments via Stripe integration
> - Notifications: Sends email and push notifications

#### Key Features
> - User authentication with JWT tokens
> - Real-time order tracking
> - Multi-payment gateway support
> - Push notifications

## 4. Project Profile

The central model of the entire application. Everything revolves around this object.

### Source

Built by `lib/profile/build-profile.ts` — a pure function that combines:
1. **Repository** (from GitHub API)
2. **Technical Facts** (from Light Analyzer)
3. **Project Understanding** (from AI Service / Groq)

### Attributes

| Attribute | Type | Description |
|-----------|------|-------------|
| `repository` | `Repository` | Repository metadata |
| `technicalFacts` | `TechnicalFacts` | Deterministic technical facts |
| `understanding` | `ProjectUnderstanding` | AI-generated project understanding |

This keeps ownership of the Project Profile inside SystemLens, not the AI provider.

---

## 5. Explanation

Represents an audience-specific explanation with a Mermaid diagram.

### Source

Generated by `lib/ai/generate-explanation.ts` → Groq API

### Attributes

| Attribute | Type | Description |
|-----------|------|-------------|
| `audience` | `Audience` | One of: CEO, PM, Developer, QA, Customer |
| `content` | string | Plain-text explanation paragraphs (no markdown formatting) |
| `diagram` | string | Mermaid `graph TD` syntax (sanitized via `mermaid-utils.ts`) |

### Audience Values

- CEO
- PM
- Developer
- QA
- Customer

### Generation Details

- Uses **lazy generation**: only the requested audience is generated (not all 5 in parallel)
- Results are cached in-memory (`lib/ai/explanation-cache.ts`) with a 30-minute TTL
- Uses **streaming**: content is streamed via SSE `chunk` events as it arrives
- After streaming completes, a `diagram` event is sent with the Mermaid diagram
- The AI response uses a delimiter-based format (`\n---DIAGRAM---\n`) to separate content from the Mermaid diagram
- Diagrams are sanitized (`sanitizeMermaid()`) and validated (`isValidMermaid()`) before being sent
- If the diagram is invalid, a deterministic fallback diagram is generated (`buildFallbackDiagram()`) based on the project's `mainModules`

## 6. Chat Message

Represents one message in the conversation.

### Source

Maintained in **browser memory** (React component state) for the current session. No database, no persistence.

### Attributes

| Attribute | Type | Description |
|-----------|------|-------------|
| `role` | `MessageRole` | `"user"` or `"assistant"` |
| `content` | string | Message text |

### Role Values

- `user` — User's question
- `assistant` — AI's response

## Relationships

### Repository → Project Profile

Repository metadata is one input to the Project Profile.

### Technical Facts → Project Profile

Technical facts contribute to the Project Profile alongside repository info and AI understanding.

### Project Understanding → Project Profile

Project understanding contributes to the Project Profile.

### Project Profile → Explanation

The Project Profile is used to generate audience-specific explanations. Only the requested audience is generated (lazy generation), with results cached in-memory.

### Project Profile → Chat Message

The Project Profile provides context for answering chat questions. The chat route uses a profile-question heuristic to skip the file-selection AI round-trip for general questions.

```
    └──► Project Profile (Profile Builder)

        ├──► Explanation (AI Service, cached in-memory, 30 min TTL)
        │
        └──► Chat (AI Service + GitHub file fetch, cached in-memory, 30 min TTL)
```

## Caching

### Disk Cache (Analysis)

- **Location**: `.cache/analysis/` directory in project root
- **TTL**: 24 hours
- **Control**: `CACHE_ANALYSIS=false` to disable
- **Content**: Full `ProjectProfile` objects (repository + technical facts + understanding)
- **Key**: SHA-256 hash of the repository URL
- **Benefit**: Re-analyzing the same repository is near-instant (skips GitHub + AI calls)

### In-Memory Cache (Explanations)

- **TTL**: 30 minutes
- **Content**: `Explanation` objects per `{ owner/name, audience }`
- **Key**: `${owner}/${name}:${audience}`
- **Benefit**: Switching between audiences is instant

### In-Memory Cache (Chat)

- **TTL**: 30 minutes
- **Contents**: 
  - File tree cache (`TreeItem[]`) per `{ owner/repo:branch }`
  - File content cache (`string`) per `{ owner/repo:path:branch }`
  - File selection cache (`ChooseFilesResult`) per `{ owner/repo:question }`
- **Benefit**: Avoids redundant GitHub API calls during chat
